# Domains Analyzer — руководство пользователя

> **Domains Analyzer** — это настольный веб-инструмент для работы со схемами доменов R-EVO.
> Он одновременно **IDE для YAML-схем** и **аналитическая платформа**: строит граф
> зависимостей доменов, ищет проблемы, проверяет PII, считает архитектурные
> метрики и помогает публиковать изменения на сервер.

## 1. Для кого это руководство

**Основная аудитория — бизнес-аналитики и системные аналитики**, работающие
с метамоделью R-EVO: сущностями, связями, атрибутами, представлениями,
правилами данных.

Также руководство будет полезно:

- **Архитекторам** — раздел «Архитектурный анализ», метрики Мартина,
  топология зависимостей, diff моделей.
- **Разработчикам схем** — редактор YAML, автокомплит, сниппеты,
  inline-валидация.
- **compliance** — раздел «PII-аудит».

**Что нужно знать заранее:** базовое понимание YAML (отступы, массивы,
объекты) и общее представление о том, что такое «домен», «сущность» и
«атрибут» в R-EVO. Всё остальное — в разделе [Словарь](#3-словарь).

## 2. Быстрый старт

### 2.1. Установка

```bash
npm install -g domains-analyzer
domna --help
domna ./domains
domna --server https://rv.local --login admin --password pass
domna ./domains --server https://rv.local --login admin --password pass
```

### 2.2. Запуск: три режима

| Режим | Команда | Что делает |
|---|---|---|
| **Локальный** | `domna ./my-domains` | Читает `.ro`-файлы с диска. Без валидации, без публикации. |
| **Гибридный** | `domna ./my-domains --server <url> --login u --password p` | Читает локальные файлы **+** серверная валидация. Публикации нет. |
| **Удалённый** | `domna --server <url> --login u --password p` | Файлы из кэша (`~/.domna/cache/`). Полный цикл: сохранение = публикация. |

### 2.3. Что вы увидите

Откройте `http://localhost:3000`. По умолчанию — **граф доменов**:

- Каждый узел — домен (`it.assets.rvision.ru`, `audit.example.com`).
- Рёбра — либо **linkage** (явные связи, зелёные), либо **FQID-ссылки**
  (Reference-атрибуты и `inherits` на другой домен, синие).
- Цвет узла: зелёный — валиден, оранжевый — missing, красный — broken.

### 2.4. Первые 5 минут — что попробовать

1. Нажмите **F** — «вписать в экран».
2. Кликните по узлу — справа откроется панель с деталями.
3. **Shift+Tab** — откройте командную палитру, введите имя домена.
4. **Ctrl+Shift+E** — каталог сущностей.
5. **Ctrl+Shift+L** — линтер схем (проверка правил).
6. **F1** — эта справка.

## 3. Словарь

### Домен (Domain)

Наименьшая единица поставки схемы. Идентифицируется FQDN
(`it.assets.rvision.ru`). Один `.ro`-файл = один домен. Может содержать
десятки сущностей, сотни атрибутов, представления, действия, правила
данных, связи, миксины.

### Сущность (Entity)

Модель объекта в домене. Например, `Asset`, `Incident`, `User`. У сущности
есть атрибуты, `id`, `name`, `label` (шаблон отображаемого имени),
опционально — родитель (`inherits`).

### Атрибут (Attribute)

Характеристика сущности: `hostname` (String), `owner` (Reference на `User`),
`status` (Workflow) и т.д. У атрибута есть `dataType`, `constraints`,
`description`.

### Связь (Linkage)

Явная связь между двумя сущностями. Тип `1_1`, `1_n`, `n_n`. Может иметь
собственные атрибуты. В отличие от Reference-атрибута, у связи есть
имя с каждой стороны (`nameFrom.side1` / `side2`) и она отображается
на графе.

### Представление (View)

UI-структура. Основные типы:

| Тип | Для чего |
|---|---|
| `entity` | Карточка сущности (панель, модалки, страница) |
| `list` | Список объектов |
| `tree` | Дерево по связям |
| `tabs_list` | Группа вкладок со списками |
| `dashboard` | Дашборд с виджетами |
| `dashboard_tree` | Дерево навигации |

Вложенные: `panel`, `modal`, `page`.

### Правило данных (DataRule)

Условное ограничение на объекты: скрыть поле, сделать обязательным,
ограничить значения. Условие задаётся через RQL.

### Миксин (Mixin)

Механизм расширения сущности данными/UI из другого домена. Позволяет
переиспользовать блоки без копирования.

### PII (Personal Identifiable Information)

Персональные данные. Спецкатегории (здоровье, религия, биометрия)
регулируются отдельно (GDPR Art. 9 / 152-ФЗ).

### Профиль генерации

Шаблон, по которому генерируются типовые блоки схемы (CRUD, дерево,
справочник, доменное меню и т.д.).

## 4. Обзор приложения

Приложение состоит из четырёх «слоёв»:

```
┌─────────────────────────────────────────────────────┐
│  Toolbar (верхняя панель)                           │
│  Модель · Фильтры · Анализ · Вид · Данные · Кеш     │
├─────────────────────────────────────────────────────┤
│  Sidebar     │   Главное поле      │  SidePanel     │
│  (сводка,    │   (граф / список)   │  (детали       │
│   теги,      │                     │   узла)        │
│   проблемы)  │                     │                │
├─────────────────────────────────────────────────────┤
│  Модалки (40+): каталог, линтер, PII, редактор, ... │
└─────────────────────────────────────────────────────┘
```

**Верхняя панель** — режимы работы, фильтры, доступ к аналитике.

**Sidebar** — обзор: сколько доменов, какие проблемы, топ по связям,
health-статистика, избранные сущности, недавние.

**Главное поле** — граф доменов или список доменов (переключается в
тулбаре).

**SidePanel** — детали выбранного узла/ребра: описание, сущности, связи,
Sonar-оценка, миксины.

**Модалки** — вся глубокая аналитика. Открываются из тулбара или
горячими клавишами.

## 5. Сценарии для бизнес-аналитика

Ниже — 15 практических сценариев. Каждый — конкретная задача, конкретные
шаги, конкретный результат.

### Сценарий 1. Познакомиться с новым проектом

**Задача:** впервые попал на проект. Нужно понять: какие домены есть,
как они связаны, где находится бизнес-логика «Активы».

**Шаги:**

1. Открыть `http://localhost:3000` (приложение уже запущено с `--server`).
2. В графе увидеть 30–50 узлов. Нажать **F** — вписать в экран.
3. В тулбаре → **Вид → Компактный режим** — если узлов много.
4. В Sidebar → **Namespaces** — увидеть группировку по семействам
   (`it.assets.*`, `it.audit.*`, `sgrc.*`).
5. Кликнуть в Sidebar → **Топ по связям** — узнать самые «центральные»
   домены (обычно это справочники и общие модели).
6. В тулбаре → **Модель → Глоссарий** (Ctrl+Shift+G) — алфавитный
   указатель всех сущностей и атрибутов проекта.
7. Ввести в поиск глоссария «Asset» — найти все сущности с этим именем.

**Результат:** вы знаете, какие домены за что отвечают, где находится
«Активы», какие домены от них зависят.

**Дополнительно:**

- **Модель → Путь изучения** — приложение построит порядок чтения
  доменов (от фундамента к верхним слоям).
- **Модель → Health Dashboard** — картина «где болит».

---

### Сценарий 2. Найти где используется поле `email`

**Задача:** нужно понять, в каких сущностях есть email, где он
отображается в UI, кто ссылается на этот атрибут.

**Шаги:**

1. **Ctrl+Shift+A** — открыть «Поиск атрибутов».
2. Ввести `email` в поиск.
3. Слева — фильтры: тип (`String`), ограничения (`required`, `regexp`).
4. В правой части — все совпадения: сущность, тип, ограничения, ссылки.
5. Клик на сущность → **«Открыть в каталоге»**.

**Как узнать «где отображается email»:**

- **Ctrl+Shift+E** → каталог сущностей → выбрать сущность → вкладка
  «Используется» (backlinks).
- Или открыть YAML-редактор (`file`-иконка) → поставить курсор на
  `attribute: email` → правая панель → **Используется** — список
  всех views / dataRules / uiRules, где упоминается `email`.

**Результат:** вы знаете все места, где email хранится и показывается.

**Дополнительно:** в правой панели «Используется» каждая строка кликабельна —
прыжок сразу к нужному view / правилу в YAML.

### Сценарий 3. Проверить схему перед публикацией

**Задача:** вы внесли изменения в `it.assets.rvision.ru` — добавили
атрибут `criticality` (Enum). Нужно убедиться, что ничего не сломано.

**Шаги:**

1. Открыть YAML-редактор (`Ctrl+Shift+E` → сущность → «Открыть файл»).
2. **Ctrl+Shift+F** → вкладка «Поиск» → проверить, что `criticality`
   встречается только там, где надо.
3. Правый верхний угол → кнопка **☁** — запустить **серверную валидацию**
   текущего (несохранённого!) YAML. Это ключевая фича: не нужно
   сохранять, чтобы проверить.
4. Если сервер вернул ошибки — они появятся **в редакторе** поверх
   локального линтера.
5. **Ctrl+Shift+L** — открыть линтер. Проверить, что нет новых
   ошибок.
6. Если baseline настроен — в линтере включить фильтр «Только новые»:
   увидите только проблемы, появившиеся после последнего «принятия».

**Результат:** вы уверены, что публикация не сломает смежные домены.

**Дополнительно:**

- **Ctrl+S** — сохранить черновик (в remote).
- **Ctrl+Shift+S** — опубликовать (проверит `version`, покажет diff).
- Перед публикацией — открывается **Publish Preview** с diff между
  текущей и опубликованной версией; если есть breaking changes —
  предупреждение.

### Сценарий 4. Аудит PII перед релизом

**Задача:** приближается аудит 152-ФЗ. Нужно выгрузить отчёт для DPO
по всем персональным данным в проекте.

**Шаги:**

1. **Ctrl+Shift+P** — открыть PII-модалку.
2. Сводка вверху: 4 категории (critical / high / medium / low),
   количество затронутых доменов и сущностей.
3. Вверху → **Экспорт отчёта** — скачивается `.md` с полным списком.
4. В отчёте — разделы: «Сводка», «Нормативная база», «По серьёзности»,
   «По доменам», «По категориям», «Полный список», «Рекомендации».
5. В самой модалке — кликнуть на домен → отфильтровать, посмотреть
   конкретные поля.

**Проверка «а нет ли у нас PII в неожиданном месте?»:**

- Фильтр по домену → искать `passport`, `cardnumber`, `снилс`.
- Если найдены — обсудить с владельцем домена.

**Ложные срабатывания:**

- Рядом с каждым атрибутом — иконка **✓** «считать не PII». Решение
  сохраняется в браузере.
- В отчёт такие атрибуты не попадают.

**Результат:** готовый отчёт для DPO, ничего не забыто.

### Сценарий 5. Безопасный рефакторинг

**Задача:** хотите переименовать атрибут `ownerId` → `responsibleId`
и поменять тип `String` → `Reference(User)`.

**Шаги:**

1. **Ctrl+Shift+E** → найти сущность → открыть в каталоге.
2. В каталоге → **«Что если удалить?»** (Deletion Simulation).
   Приложение покажет: кто ссылается, какие views сломаются, какие
   dataRules затрагиваются.
3. Из списка «Reference» — увидеть все места, где `ownerId`
   используется. Каждое — с переходом.
4. Открыть каждое место, оценить.
5. Перед изменением **типа** — открыть YAML-редактор, изменить
   `dataType` + `entity: User`.
6. **Ctrl+Shift+S** — публикация → Publish Preview → если breaking
   changes, приложение предупредит.

**Проверка «не сломал ли я представления»:**

- В редакторе — правая панель → **Используется**. Все views с
  `attribute: ownerId` теперь будут подсвечены как broken.
- Или откpыть **DomainSchemaModal** (схема домена) — там карточка
  сущности с виджетами и атрибутами.

**Дополнительно:**

- Если делаете массовый рефакторинг — **Model Diff** покажет, что
  изменилось на уровне всей модели.
- **Baseline** (в линтере) — если вы приняли текущее состояние до
  рефакторинга, увидите только новые проблемы.

### Сценарий 6. Создать новый домен

**Задача:** новый проект — нужен домен `risk.management.example.com`.

**Шаги:**

1. Тулбар → **Вид → Список** (переключиться из графа в список).
2. Над списком → **Новый домен**.
3. Заполнить:
   - `ID`: `risk.management.example.com` (валидация FQDN)
   - `Название`: `Управление рисками`
   - `Автор`, `Теги`, `Описание`
   - `Шаблон`: выбрать один из 6 (пустой, справочник, реестр активов,
     библиотека типов, инциденты, контейнер для миксинов).
4. **Создать**.

**Что происходит:**

- **Local**: создаётся `.ro`-файл в указанной папке.
- **Remote**: создаётся expertise на BFF (черновик) + `.ro` в кэш.

**Результат:** новый домен появился в списке, граф пересобрался,
открылся редактор.

**Дополнительно:**

- После создания — зайдите в **Схему домена** и проверьте, что
  шаблон применился корректно.
- Если шаблон не подошёл — можно удалить домен (с симуляцией
  зависимостей).

### Сценарий 7. Массовая генерация CRUD для всех сущностей

**Задача:** домен состоит из 30 сущностей, для каждой нужны действия,
представления, меню.

**Шаги:**

1. Тулбар → **Модель → Схема домена** → внизу **«Сгенерировать для домена»**.
2. Откроется **GenerateBatchModal**.
3. Профиль: `crud` (или `auto` — авто-выбор по флагам).
4. Чекбоксы:
   - [x] Создать корневое меню (root_group)
   - [x] Добавить базовые иконки
5. Все сущности выбраны по умолчанию.
6. **Генерация** — стриминг в реальном времени: каждая сущность
   отмечена как «done» с количеством сгенерированных блоков.
7. **Применить** — открывается YAML-редактор, блоки вставляются в
   файл. Preflight — проверка, что линтер не ругается.

**Результат:** 30 сущностей «обвязаны» CRUD-блоками за один заход.
Файл помечен как изменённый, дальше — обычная публикация.

**Дополнительно:**

- После применения в YAML — блоки показаны в **Манифесте** (см. сценарий 11).
- Если что-то сгенерировалось не так — открыть в редакторе и удалить
  блоки вручную (манифест при следующей генерации покажет их как
  orphaned).

### Сценарий 8. Разобраться, что изменилось после обновления

**Задача:** пришло уведомление, что на сервере обновили 5 доменов.
Нужно понять, что изменилось.

**Шаги:**

1. Тулбар → **Данные → Что изменилось в модели**.
2. Откроется **ModelDiffModal**. Показан diff между снапшотом
   (сделанным при последнем запуске) и текущим состоянием модели.
3. Таб «По доменам» — сгруппировано по доменам. Для каждого — список
   добавленных / удалённых / изменённых сущностей, типов данных,
   миксинов.
4. Таб «По типам» — плоский список изменений.
5. Клик на сущность — открывается каталог на этой сущности.

**Также:**

- Тулбар → **Кеш** (иконка базы) → проверить, есть ли outdated домены.
- Если есть — кнопка **«Обновить кеш»** → загрузит свежие `.ro`.
  После обновления — **Model Diff** покажет, что именно изменилось
  между старым и новым кэшем.

**Результат:** знаете, какие изменения пришли с сервера, кто и что
затронул.

### Сценарий 9. Сравнить два домена

**Задача:** два похожих домена (prod и staging, или два разных
проекта с одинаковой моделью активов). Нужно найти различия.

**Шаги:**

1. Тулбар → **Модель → Сравнить домены**.
2. Выбрать домен A и домен B.
3. Сводка вверху: количество сущностей, атрибутов, Sonar-оценка.
4. Секции:
   - **Только в A** — сущности, которых нет в B.
   - **Только в B** — наоборот.
   - **Общие с различиями** — сущности, которые есть в обоих, но
     отличаются (атрибуты, `inherits`, `name`).

**Пример практического использования:**

- В prod есть `Asset.ownerId`, в staging уже `Asset.responsibleId` —
  видно, что рефакторинг был только в staging.

**Результат:** чёткая картина различий.

**Дополнительно:**

- Для двух версий **одного** домена (prod сейчас vs prod раньше) —
  используйте **Model Diff** (сценарий 8).

### Сценарий 10. Проверить здоровье проекта

**Задача:** ежемесячный health-check. Как дела у схем в целом?

**Шаги:**

**Дополнительно:**

- **Архитектурные метрики (Мартина)** — Ctrl+Shift+Y. Показывает,

### Сценарий 11. Восстановить случайно удалённый блок

**Задача:** при правке YAML случайно удалили `actions_createIoc`.
Нужно восстановить.

**Шаги:**

1. Открыть YAML-редактор домена.
2. Правая панель → **Модель → Сгенерированные блоки** — открывает
   **GeneratedManifestModal**.
3. Найти сущность `Ioc`.
4. В списке блоков — `actions_createIoc` со статусом
   **«удалён из YAML»**.
5. Кнопка **↩ Восстановить** — открывает YAML с уже подставленным
   блоком на правильном месте.

**Результат:** блок восстановлен с правильными зависимостями
(виджет `buttons_createIoc` тоже подтянется, если его нет).

**Дополнительно:**

- **Манифест** — это sidecar-файл `_generated.json` в корне домена.
  Хранит «что было сгенерировано и когда».
- Статусы блоков:
  - **актуален** — сгенерирован, не менялся.
  - **изменён вручную** — сгенерирован, потом правили.
  - **удалён из YAML** — был, но больше нет.
- При повторной генерации manifest помогает не перезаписать ручные
  правки.

### Сценарий 12. Понять, зачем нужен «фокус» и «путь»

**Задача:** в графе 100 узлов, вы хотите понять окружение одного
конкретного домена.

**Фокус** — двойной клик по узлу. Показывает только соседей глубины N
(настраивается в тулбаре «Анализ → Глубина фокуса»).

**Путь** — тулбар «Анализ → Найти путь»: кликнуть по первому узлу,
потом по второму. Приложение найдёт кратчайший путь и подсветит его
жёлтым.

**Циклы** — тулбар «Анализ → Найти циклы» (горячая клавиша **C**).
Подсветит SCC (компоненты сильной связности) — где есть циклические
зависимости.

**Результат:** вы видите только релевантную часть графа.

### Сценарий 13. Понять, что чем можно удалить

**Задача:** есть подозрение, что в домене много «мёртвого кода» —
сущности/атрибуты, которые нигде не используются.

**Шаги:**

1. **Ctrl+Shift+E** → каталог сущностей → фильтр «Только сироты»
   (`stats.orphanEntities`).
2. Или **Ctrl+Shift+B** — матрица атрибутов. Список атрибутов,
   встречающихся только 1 раз (`singletons`).
3. Открыть YAML-редактор → **Меню (…) → Затенять неиспользуемые**.
   Неиспользуемые атрибуты подсветятся серым.
4. **Ctrl+Shift+L** → линтер → категория «Рекомендации» →
   `recommended/entity-description`, `recommended/attribute-description`.

**Результат:** список кандидатов на удаление.

**Осторожно:** «не используется» ≠ «не нужно». Атрибут может быть в
процессе внедрения, использоваться в API/scenario, упоминаться в
бизнес-документации. Удалять — только после согласования.

### Сценарий 14. Понять порядок установки

**Задача:** есть 40 доменов, нужно понять, в каком порядке их
устанавливать на чистый сервер (зависимости).

**Шаги:**

1. Тулбар → **Модель → Порядок установки** (TopoSort).

3. Учитывать зависимости: FQID-ссылки, linkage, missing-домены.
4. **Построить порядок** — уровни от «нулевых зависимостей» к
   «зависимым».
5. Критический путь — самая длинная цепочка.
6. Кнопка **«На графе»** — раскрасить узлы по уровням.

**Результат:** уровни установки (1, 2, 3…) с указанием, что от чего
зависит.

**Дополнительно:** экспорт в MD или JSON для отчёта.

### Сценарий 15. Валидация без сохранения

**Задача:** вы правите YAML, но не хотите сохранять — пока не
убедитесь, что серверная валидация не ругается.

**Шаги:**

1. Открыть YAML-редактор.
2. Разблокировать (двойной **Shift**).
3. Внести правки.
4. Нажать **☁** в правом верхнем углу — кнопка «Проверить на сервере».
5. **Не сохраняем** — отправляется текущее содержимое Monaco.
6. Через 2–5 секунд — ответ:
   - ✅ зелёная галочка — валидно.
   - ❌ красный крестик + список ошибок — в правой панели «Сервер».
7. Ошибки появились в редакторе поверх линтера. Клик по ошибке —
   прыжок к строке.
8. Когда уверены — **Ctrl+S** (черновик) или **Ctrl+Shift+S**
   (публикация).

**Результат:** вы валидируете без побочных эффектов.

## 6. Главный экран

### 6.1. Граф

Классический node-link граф:

- **Узлы** — домены. Размер фиксирован (300×88 или 42×42 в компактном).
- **Рёбра**:
  - **Linkage** (зелёные) — явные связи между сущностями разных доменов.
  - **FQID** (синие) — Reference-атрибуты и `inherits`, пересекающие
    границу домена.
- **Missing** (оранжевые) — FQID ссылается на домен, которого нет в кэше.
- **Broken** (красные) — YAML не парсится, файл повреждён.

**Интерактивность:**

- Клик — выделить, показать в панели.
- Двойной клик — фокус (глубина настраивается).
- Правый клик — контекстное меню (фокус, dependents, пути, скрыть,
  в избранное).
- Hover — тултип с деталями.

**Панели управления:**

- **Левая верхняя**: вписать, переуложить, сбросить, назад/вперёд.
- **Правая нижняя**: MiniMap.
- **Левая нижняя**: zoom controls.

**Режимы отображения:**

- **Обычный** / **компактный** — переключается в тулбаре или «Вид».
- **Heatmap**: health / degree / entities / fqid. Узел окрашивается
  по шкале.
- **Группировка**: рамки-кластеры по семействам / каталогам.
- **Bidirectional**: объединение A↔B в одно ребро.

**Кластеры:** при `layout = cluster/folder` — полупрозрачные рамки
поверх графа с подписями и количеством.

## 7. Инструменты анализа модели

Все открываются из тулбара → **Модель** или горячими клавишами.

### 7.1. Каталог сущностей (Ctrl+Shift+E)

Табличная вью на все сущности всех доменов.

**Левая панель:**

- Поиск по id, name, description, атрибутам.
- **Домены** — чипы (клик = фильтр).
- **Теги** — чипы.
- **Свойства**: только с родителем / только с миксинами / только сироты.
- **Минимум ссылок**: слайдер (0–20).
- **Сброс**.

**Правая панель:**

- Таблица: сущность / домен / наследует / атрибутов / ссылок / миксины / теги.
- Строка: клик → открыть **Impact Analysis Panel**.
- **Звёздочка** слева — в избранное.
- **Открыть в каталоге** — детальная панель:
  - Метаданные (name, label, description).
  - Цепочка наследования.
  - Атрибуты с типами, ограничениями, ссылками.
  - **Кто наследует**.
  - **Кто ссылается** (Reference).
  - **Куда ссылается** (исходящие Reference).
  - **Связи** (linkage).
  - **Миксины**, расширяющие сущность.
  - Кнопка **«Что если удалить?»** — симуляция удаления.

**Практический совет:** сочетание «Только сироты» + «Минимум ссылок = 0»
даёт список сущностей, которые не используются вообще. Отличная отправная
точка для ревизии.

### 7.2. Поиск атрибутов (Ctrl+Shift+A)

Поиск по всем атрибутам **всех** сущностей **всех** доменов.

**Слева — фильтры:**

- Поиск (id + name + description).
- Тип данных: String, Reference, Array, custom Enum/Workflow/Table.
- Ограничение: required, unique, regexp, length, range, size, mime_types.
- Домены (чипы).
- **Только PII** — фильтр по найденным PII-атрибутам.

**Справа — режимы:**

- **Сводка по именам** — если поиск пустой: список всех базовых имён
  атрибутов с количеством сущностей. Клик — поиск по этому имени.
- **Все атрибуты** — плоский список.
- Строка: id + name + чип сущности (клик → каталог) + тип +
  Reference + constraints + PII-бейдж + кнопка **«Детали»** →
  разворачивается с описанием, полным id, вложенными.

**Практический совет:** введите `email` — увидите все email-атрибуты
во всех сущностях. Удобно для аудита «где хранятся контакты».

### 7.3. Матрица связей (Ctrl+Shift+M)

### 7.4. Матрица атрибутов (Ctrl+Shift+B)

**Настройки:**

- Минимум упоминаний (по умолчанию 2).

**Практический совет:** колонки с предупреждением ⚠ — атрибуты с
разными типами в разных сущностях. Хороший индикатор

### 7.5. Глоссарий (Ctrl+Shift+G)

Алфавитный указатель.

- **Атрибуты** — все имена атрибутов, с контекстом «в какой сущности».
- **Типы данных** — все custom Enum/Workflow/Table.

**Использование:**

- Клик на букву — быстрый прыжок.
- Клик на элемент — открыть в каталоге.

**Практический совет:** перед введением нового атрибута проверьте

## 8. Качество и соответствие

### 8.1. Линтер схем (Ctrl+Shift+L)

Основной инструмент проверки **правил**.

**Сводка вверху:**

- Ошибки (error).
- Предупреждения (warning).
- Рекомендации (info).
- Sonar-оценка (score / grade).

**Фильтры:**

- Категория: именование, обязательные поля, рекомендации, ссылки,
  семантика, валидация, UI rules.
- Домен (с 📌 если baseline установлен).
- **«Только новые»** — если baseline есть.

**Список проблем, сгруппированный по правилу:**

- Заголовок правила (клик — развернуть).
- **📖 Шпаргалка** — рядом с категорией, открывает нужный раздел.
- Каждая проблема:
  - Сообщение.
  - 💡 Подсказка (что делать).
  - Контекст (сущность, атрибут) — кликабельный.
  - **В редакторе** — клик на всю строку → открывает YAML на нужной
    строке.
  - 🔥 new — если проблема появилась после baseline.

**Категории правил:**

| Категория | Что проверяет |
|---|---|
| naming | camelCase, PascalCase, длина id |
| required | обязательные поля (`name` у сущности) |
| recommended | `description`, `label` |
| reference | ссылочная целостность |
| semantic | дубликаты, циклы, сироты |
| validation | типы данных, constraints |
| uirules | правила UI |

**Sonar-оценка** — общий балл 0–100 с весом категорий:
- reference×5, semantic×4, uirules×3, naming×2, validation×2, required×1, recommended×1.

**Оценки:**

- A (≥90) — отлично.
- B (75–89) — хорошо.
- C (60–74) — приемлемо.
- D (40–59) — плохо.
- E (<40) — критично.

## 9. Архитектурный анализ

### 9.1. Метрики Мартина (Ctrl+Shift+Y)

Классические метрики из «Чистой архитектуры».

**Метрики:**

| Метрика | Формула | Что означает |
|---|---|---|
| **Ca** | — | Сколько доменов зависят от этого |
| **Ce** | — | От скольких зависит этот |
| **I** | Ce / (Ca + Ce) | Instability: 0 = стабильный, 1 = нестабильный |
| **A** | abstract entities / total | Abstractness |
| **D** | \|A + I − 1\| | Distance от идеальной линии |

**Зоны:**

- **Main sequence** (D < 0.3) — норма.
- **Pain zone** (A < 0.3, I < 0.3) — стабильный и конкретный.
  Менять больно, абстракций нет.
- **Uselessness** (A > 0.7, I > 0.7) — абстрактный и нестабильный.
  Мёртвый код или недоделанный модуль.

**Что видно:**

- **Scatter-plot I × A** — все домены точками. Идеальная линия —
  диагональ.
- **Таблица** с сортировкой по любой метрике.
- **Фильтр по зоне** — «показать только Pain Zone».

**Практический совет:**

- Pain Zone — топ-приоритет для рефакторинга.
- Uselessness — кандидаты на удаление/переиспользование.
- Не гонитесь за D=0 у всех: главное, чтобы Pain Zone была пуста.

### 11.1. Открытие

Из любого места, где есть кнопка «Открыть файл» / «Редактор»:

### 11.2. Интерфейс

```
┌─────────────────────────────────────────────────────────────┐
│  Шапка: имя файла · домен · статус · Save/Publish · ...     │
├─────────────────────────────────────────────────────────────┤
│  Табы (несколько открытых файлов)                           │
├─────────────────────────────────────────────────────────────┤
```

### 11.3. Шапка

- **Имя файла** + домен (badge).
- Статус черновика (draft badge).
- Diff badge (если открыт diff).
- Lock / Edit mode badge.
- Save/Publish status: `● сохранение…`, `✓ сохранён`, `● изменён`,
  `+N −M` (diff count).
- Stale issues: `⚠ N устарели` — если issues из серверного линтера
  могли устареть после правок.
- Meta: `опубликовано v1.2.3 · сохранён 2 часа назад · Иван П.`

**Кнопки:**

- **Сохранить** (Ctrl+S) — сохранить черновик.
- **Опубликовать** (Ctrl+Shift+S) — публикация с повышением version.
- **🔒 / 🔓** — Lock / Edit.
- **📋** — копировать в буфер.
- **🔍** — Diff previous (если есть предыдущее сохранение).
- **☁** — Diff с опубликованной (если открыт draft).
- **☁** — серверная валидация.
- **⋯** — меню (схема домена, генерация, PII, сравнение, показать на
  графе, скрыть навигацию, скрыть панель проблем, проверки on/off,
  затенение unused, справка).
- **✕** — закрыть.

### 11.4. Навигация (левая панель)

Три таба:

**Навигация:**

- Секции (`entities`, `linkages`, `views`, …) сворачиваются/разворачиваются.
- Дерево `- id:` внутри: сущность → её атрибуты, view → widgets и т.д.
- Клик по id — прыжок к строке.
- Наведение — активация (для стрелок).
- ⚠ рядом с сущностью — есть проблемы.
- Наведение на ⚠ — тултип с первыми 5 проблемами.
- **Фильтр** вверху: `только проблемные` + поиск по id.
- **Кнопки**: ⤢ (развернуть всё), ⤡ (свернуть всё).
- **Ресайз** — тянуть за правую границу (180–600px).

**Поиск** (Ctrl+Shift+F):

- Многострочный поиск (можно переносить строку — Ctrl+Enter для
  следующего матча).
- Опции: `Aa` (регистр), `.*` (regex), `\b` (целое слово),
  `#` (включая комментарии).
- Найденные матчи сгруппированы по секциям.
- Клик — прыжок к матчу + подсветка в редакторе.
- **Ctrl+Enter** — следующий матч, **Ctrl+Shift+Enter** — предыдущий.
- **↑ / ↓** — то же (если query однострочный).

**Закладки** (F2):

- **F2** на строке — toggle закладку.
- **F2** без выделения на строке с закладкой — прыжок к следующей.
- В табе «Закладки» — список с текстом строки.
- Клик — прыжок.
- **✕** — удалить одну.
- **Delete sweep** в шапке — удалить все.
- Закладки сохраняются per-file в localStorage.

### 11.5. Quick Jump (Shift+Tab)

Быстрый переход по файлу. Открывается **Shift+Tab** (в любом месте
редактора).

**Синтаксис:**

| Что | Как |
|---|---|
| Поиск по id, name, описанию, FQID | `audit` |
| По секции | `#entities` / `#entities audit` |
| По строке | `:42` / `:42:5` |
| По содержимому | `>id:` |
| Regex | `>/lists_\w+/i` |
| Атрибут кросс-сущностно | `@score` |
| Проблема линтера | `!error` / `!audit` |
| Соседи курсора | `~` / `~audit` |
| Справка | `?` |
| Точный FQID | `it.assets.rvision.ru/AssetGroups` |

**Клавиши:**

- **↑ / ↓** — навигация.
- **Enter** — перейти.
- **Ctrl+Enter** — топ-1.
- **Alt+← / →** — история прыжков.
- **Ctrl+Alt+↑ / ↓** — предыдущая/следующая секция.

- **🔗 «Поделиться»** — ссылка с `#q=<query>`. Открытие такой ссылки

**Практический совет:** `~` — самая полезная команда. Когда нужно

### 11.7. Валидация

Три уровня, работают одновременно:

**Уровень 1: Inline-маркеры** (жёлтые/красные подчёркивания прямо в тексте):

- `attribute-validator`: camelCase, уникальность id, дубликаты,
  системные id, description.
- `fqid-validator`: FQID ссылки на сущности/связи.
- `dataType-validator`: базовые + кастомные типы.
- `view-ref-validator`: ссылки на views / groups / блоки.
- `attribute-ref-validator`: `attribute:` в `searching`, `sorting`,
  `projection`.
- `ui-rule-validator`: widget / group / column / preset в `uiRules`.
- `enum-validator`: значения enum-полей (`type`, `effect`, `target`,
  `direction`, …).
- `rql-check`: RQL-выражения.
- `action-required-validator`: обязательные поля action по type.

**Уровень 2: Серверный линтер** (`dg-linter`):

- Проблемы, которые нашёл линтер на сервере (на сохранённой версии).
- Маркеры **обновляются на лету** при правках: `classifyIssue` для
  каждой проблемы решает:
  - `still` — проблема осталась.
  - `resolved` — исправлена (маркер исчезает).
  - `unknown` — проверить нельзя, но маркер не исчезает.
- Клик на маркер → действие (справка, переход к линтеру, игнор).

**Уровень 3: Серверная валидация** (☁ кнопка):

- Проверка **текущего** содержимого Monaco на сервере R-EVO.
- Не требует сохранения.
- Ошибки приходят с сервера (Zod-схема) и подсвечиваются поверх
  локальных.

**Правая панель → вкладка «Проблемы»:**

- Сгруппировано по правилу (default) или по сущности (переключатель).
- Фильтр severity: ошибки / предупреждения / инфо.
- Каждая проблема:
  - Если `__isUnknown` — значок ⏱ (требуется сохранение, чтобы
    серверный линтер перепроверил).
  - Кликабельная — прыжок к строке.

**Quick Fix (лампочки 💡):**

- В gutter слева, если есть actionable фикс:
  - 🐫 Переименовать в camelCase.
  - 🏷️ Добавить `label`.
  - 📝 Добавить `description`.
  - 📖 Показать справку.
  - 🔬 Открыть линтер.
- **Ctrl+.** или **Alt+Enter** — открыть меню фиксов.
- Работают и в заблокированном файле (авторазблокировка при применении).

**Включение/выключение проверок:**

- Редактор → **⋯ меню → Выключить/Включить проверки**.
- Состояние сохраняется в localStorage.

### 11.8. Автокомплит и сниппеты

**Автокомплит** — контекстный. Понимает, где стоит курсор, и
предлагает:

- **Поля** — обязательные (required) сверху, потом опциональные,
  потом системные.
- **Значения** — `dataType:` → список типов, `type:` → enum'ы по
  контексту (widget / action / linkage / view…), `inherits:` /
  `entity:` / `side1:` — сущности, `attribute:` — атрибуты
  контекстной сущности.
- **Ref-поля** — id из текущего домена + FQID из других.
- **Сниппеты** — префикс `new*`.

**Как работает контекст:**

- Path-based: `views.widgets.control` → понимает, что это control
  виджета (и для `type: linkage` даёт `select`/`table`, для
  `type: action` — `regular_button`/`dropdown`).
- Значения `dataType` — базовые + кастомные.
- В `attribute:` — системные + кастомные + атрибуты **цепочки
  наследования**.
- В `searching[].attribute` — только атрибуты текущей сущности.
- В `filter.attributes.use[].attribute` — атрибуты сущности из
  `source.entity` list-view.

**Сниппеты (префикс `new`):**

| Префикс | Что вставляет |
|---|---|
| `newentity` | Новая сущность с примером атрибута |
| `newattr` / `newref` / `newarr` | Атрибуты (базовый / Reference / Array) |
| `newidentifier` | Identifier с шаблоном |
| `newlinkage` | Связь 1_n |
| `newaction` / `newbulkdelete` / `newbulkedit` | Действия |
| `newview` / `newlist` / `newentityview` | Views (entity / list / full) |
| `newwidget` / `newwidgetattr` / `newwidgetlinkage` | Виджеты |
| `newgroup` / `newblock` / `newtab` / `newform` | Группы |
| `newpanel` / `newmodal` / `newpage` | Nested views |
| `newrule` / `newuirule` / `newuirulevariant` | Правила |
| `newsequence` / `newmedia` / `newtree` / `newtransitive` | Прочее |
| `newmixin` / `newmixinview` / `newmixinlinkage` | Миксины |
| `newmenuroot` / `newmenuitem` | Меню |

| `newexchange` | exchangeSettings |

Полный список — в **Шпаргалке** (Ctrl+Shift+L → 📖 рядом с
категорией, или редактор → **⋯ меню → Шпаргалка**).

### 11.9. Сохранение

**Ctrl+S** — сохранить.

**Что происходит (remote-режим):**

1. Валидация: если YAML сломан — предупреждение «Сохранить всё равно?».
2. Проверка mtime (файл не изменился вне редактора?).
3. Запись `.ro` на диск.
4. Копирование `.ro` в `.previous/`.
5. **saveDraft** на сервере (черновик, не публикация).
6. Обновление `_index.json`: `hasDraft = true`.
7. Пересборка модели (rebuild) — **до** ответа клиенту.
8. Read-back: сверка содержимого на диске с Monaco.
9. Обновление `_generated.json` (манифест).

**Что происходит (local/hybrid):**

1. Запись `.ro` на диск.
2. Копирование в `.previous/`.
3. Никаких серверных операций (кроме hybrid — там серверная
   валидация недоступна в save).

**Индикаторы:**

- В шапке: `● сохранение…` → `✓ сохранён`.
- Snackbar с подтверждением.

---

### 11.10. Публикация (Ctrl+Shift+S)

**Доступна:**

- **Remote**: полный цикл (draft → public).
- **Hybrid**: **недоступна** (кнопка disabled, tooltip объясняет).
- **Local**: сохранение с bump version (без сервера).

**Что происходит:**

1. Проверка version: если не изменилась — предложение bump
   (smart: MAJOR/MINOR/PATCH по impact).
2. **Publish Preview** — модалка с diff:
   - Версия: сервер → новая.
   - Added entities.
   - Removed entities (breaking!).
   - Changed entities (с типом изменений).
3. Подтверждение — публикация.
4. `publishExpertise` на сервере.
5. `_index.json`: `hasDraft = false`, `version = newVersion`,
   `updatedAt = now`.
6. Инвалидация кеша `published`.

**Если публикация отклонена:**

- Ошибка `EXPERTISE.PUBLISH.LOWER_VERSION` — версия ниже серверной.
- Zod-ошибки — из `details` собирается читаемое сообщение.
- Ошибка показывается в шапке (`❌ saveError`).

**Практический совет:** всегда проверяйте Publish Preview. Если там
«Removed entities» — это breaking change, потребители сломаются.

---

### 11.11. Diff

Два режима:

**Diff previous** — 🔍 кнопка (если есть `.previous`):
- Сравнение с предыдущим сохранением на диске.
- Side-by-side в отдельном контейнере Monaco.

**Diff published** — ☁ кнопка (только в remote с draft):
- Сравнение текущего Monaco с **опубликованной** версией.
- Скачивается с сервера через `/file/published`.
- Показывает, что «будет опубликовано».

**Практический совет:** если вы открыли draft и хотите понять «что
изменилось после публикации» — Diff published даёт ответ.

---

### 11.12. Восстановление изменений

При открытии файла с несохранёнными изменениями из прошлой сессии:

1. В `sessionStorage` лежит бэкап (`dg-yaml-backup:<filePath>`).
2. Если хэш `savedContent` совпадает с файлом на диске — предложение
   «Восстановить правки от HH:MM?».
3. При восстановлении — редактор открывается в режиме редактирования.

**Ограничения:**

- `sessionStorage` — 5 МБ. Для больших YAML (>5МБ) автосохранение
  тихо отключается.
- Бэкап очищается после успешного сохранения.
- Бэкап per-вкладка (session-scoped).

### 11.13. Режимы (Lock / Edit)

Редактор по умолчанию **заблокирован**. Это безопасность: случайное
нажатие клавиши не портит YAML.

**Разблокировать:**

- Кнопка **🔒** в шапке.
- Двойной **Shift** (быстро, из любого места).

**Заблокировать:**

- Кнопка **🔓**.
- Двойной **Shift**.
- При попытке закрыть с изменениями — предложение сбросить.

**Особенности:**

- В заблокированном режиме — навигация и поиск работают.
- **Quick Fix (лампочки)** работают в обоих режимах.
- Применение quick fix **авторазблокирует** файл.

**Практический совет:** двойной Shift — самый быстрый способ
переключения. Если Shift нажат дважды без других клавиш между — режим
меняется.

### 11.14. Focus (фокус)

Из навигации: правый клик на сущности/связи → **Фокус** или
**Фокус с зависимостями**.

- **Фокус** — затеняет всё, кроме primary (выбранного элемента) и
  secondary (всех мест, где он упоминается).
- **Фокус с зависимостями** — добавляет tertiary: dataTypes,
  sequences, counterColorPatterns, на которые ссылаются атрибуты
  primary/secondary.

**Визуально:**

- Primary — не затеняется.
- Secondary — не затеняется.
- Tertiary — светло-серый фон.
- Остальное — сильно затенено.

**Плашка сверху:**

- Имя элемента.
- `N / M строк` — сколько строк связано.
- Чекбокс **«Зависимости»** (включить tertiary).
- **✕** — снять фокус.

**Практический совет:** когда правите сущность и хотите видеть только
её окружение — Focus с зависимостями.

## 12. Генератор схем

### 12.1. Профили

Генератор работает по **профилям** — шаблонам, по которым создаются
типовые блоки.

**Профили для сущности:**

| Профиль | Что делает |
|---|---|
| `crud` | Полный CRUD: actions + views + list + panel + modals + menu + medias |
| `crud-with-page` | CRUD + pages_infoX (требует root_group) |
| `dictionary` | Только entity-view с editors (справочник) |
| `no-modals` | Read-only: list + panel, без форм |
| `tree-view` | Иерархический просмотр по side-1 связям |
| `technical` | Ничего не генерирует (помечает «без UI») |
| `tabs-list` | Tabs_list с выбранными list-view |
| `sorting-searching` | `sorting[]` + `searching[]` |
| `transitive-chain` | `transitiveLinkages[]` + join-виджет + колонка |
| `defaults` | `dataRules.default` для Bool/Enum/Workflow |
| `auto` | Авто-выбор по флагам сущности |
| `linked-groups` | `linked_objects_groups` виджеты |

**Профили для домена:**

| Профиль | Что делает |
|---|---|
| `domain-extras` | Корневое меню + пункты меню + палитра иконок |
| `enum-workflow-builder` | Скелеты Enum/Workflow для String-атрибутов |
| `ui-status-colors` | Заполняет `view[]` в Enum/Workflow |
| `exchange-settings` | Скелет `exchangeSettings` |
| `counter-color` | `counterColorPatterns[]` для Counter-атрибутов |

**Открытие (single):**

Тулбар → **Модель** (или прямо из схемы домена/каталога) →
«Сгенерировать» → **GenerateSchemaModal**.

- Выбор сущности (для entity-профиля).
- Выбор профиля — карточка с описанием.
- Параметры профиля (include bulk, tree-type, chain, …).
- **Block list** — что будет сгенерировано.
- **YAML** — превью каждого блока.
- **Diff** — «сейчас в YAML» vs «после применения».
- **Проблемы** — preflight.
- **Пропущено** — skipped с причиной и подсказкой.
- **Применить** — вставка в YAML + открытие редактора.

**Статусы блоков:**

- **Без статуса** — новый блок.
- **✓ есть** — уже в YAML и совпадает с моделью. Не аппендится.
- **⚠ модель изменилась** — сгенерировано ранее, модель поменялась.
  Будет **заменён**.
- **✎ правка вручную** — YAML правили после генерации. Не
  перезаписывается (если не включить «Перезаписывать изменённые
  вручную»).
- **⊘ удалён из YAML** — был сгенерирован, но удалён. Поставьте
  галку, чтобы восстановить.

**Практический совет:** `crud` с включённой опцией
`excludeReadonlyFromCreate` даёт более чистые формы создания — без
readonly-полей.

---

### 12.2. Пакетная генерация

Тулбар → **Модель → Схема домена → «Сгенерировать для домена»** или
из меню инструментов.

- Выбрать профиль (только entity-профили).
- Выбрать сущности (все / выборочно).
- Дополнительные опции:
  - **Создать корневое меню (root_group)** — обвязка домена.
  - **Добавить базовые иконки** — 10 стандартных.
- **Генерация** — стриминг, прогресс по каждой сущности.
- **Применить** — открытие YAML с batch-вставкой.

**Практический совет:** профиль **`auto`** + «создать меню» +
«создать иконки» — самый быстрый способ «оживить» новый домен.

---

### 12.3. Манифест

Sidecar-файл `_generated.json` в корне домена.

Хранит для каждой сущности:

- профиль,
- `generatedAt`,
- список блоков с `blockId`, `hash`, `title`, `parentViewId`,
  `generatedAt`.

**Использование:**

- Открывается через **Сгенерированные блоки** в схеме домена или в
  редакторе (`⋯ меню`).
- Показывает: сколько блоков, сколько актуально / изменено / удалено.
- Фильтр: все / только проблемные.
- **↩ Восстановить** — восстановить удалённый блок.
- **✕ Очистить манифест** — начать с чистого листа (не трогает
  YAML).

**Как работает (внутри):**

- `hashPayload` от payload блока при генерации.
- При следующем открытии манифеста: сравнение текущего payload
  (найденного по `blockId` в YAML) с сохранённым hash.
- Совпало — `actual`. Не совпало — `modified`. Не найдено —
  `orphaned`.

**Практический совет:** если вы вручную правите сгенерированные блоки —
манифест это запомнит. При следующей генерации предложит «не трогать
изменённые вручную».

## 15. Три режима работы с сервером

### 15.1. Local

```bash
npm start -- ./my-domains
```

- Читает `.ro` из `./my-domains`.
- Никаких серверных вызовов.
- Редактор работает, save = запись на диск.
- Валидация только локальная (inline-проверки).
- Publish недоступен.

**Когда использовать:** работа с локальной копией, разработка
без доступа к серверу.

---

### 15.2. Hybrid

```bash
npm start -- ./my-domains --server https://server.com --login u --password p
```

- Файлы **локальные**.
- Логин на сервер при старте (для валидации).
- Save = запись на диск, publish = недоступен.
- Серверная валидация **доступна**.

**Когда использовать:** правки локально, но хочется проверять схему
на сервере перед пушем.

---

### 15.3. Remote

```bash
npm start -- --server https://server.com --login u --password p
```

- Файлы из кэша `~/.domna/cache/domains/<host>__<hash>/`.
- Save = draft на сервере + запись в кэш.
- Publish = публикация на сервере.
- Серверная валидация доступна.
- Publish Preview с diff.

**Дополнительные флаги:**

- `--refresh` — обновить кэш всегда.
- `--refresh 1d` — обновить, если кэш старше 1 дня.
- `--reset-cache` — удалить кэш перед загрузкой.
- `--secure` — проверять TLS-сертификат.

**Обновление кэша из UI:**

- Тулбар → иконка базы (Кеш) → **«Обновить кеш»**.
- Или **Model Diff → Обновить**.

**Когда использовать:** основная работа с актуальными схемами.

---

### 15.4. Outdated check

## 16. Лучшие практики

### 16.1. Именование

- **Домены** — FQDN (`it.assets.rvision.ru`).
- **Сущности** — `PascalCase`, без разделителей. `Asset`, `UserConfig`.
- **Атрибуты** — `camelCase`. `hostname`, `ownerId`. **Без точек**
  (точка = наследование).
- **DataTypes** — `PascalCase`. `enumIocTypes`, `AuditStatusWorkflow`.
- **Views / Actions** — `camelCase` с осмысленным префиксом:
  `lists_`, `view`, `panels_`, `forms_`, `pages_`, `treeView_`,
  `tabs_`, `actions_`, `buttons_`, `editors_`, `blocks_`, `menus_`,
  `icons`.
- **Route** — `/path/segment`, только строчные + цифры + дефис.

Полный чек-лист — в **Шпаргалке** (Ctrl+Shift+L → 📖 → «Ограничения
идентификаторов»).

---

### 16.2. Baseline workflow

1. Первый запуск — принять baseline (`📌 Принять для всех`).
2. Работаете неделю — вносите правки.
3. В линтере → **«Только новые»** — видите только свои регрессии.
4. Перед релизом — **📌 Обновить baseline** для всех доменов.
5. Следующая неделя — снова сравнение только с новым baseline.

**Практический совет:** включите baseline в CI:
`generate + lint + take-baseline + diff`. Если diff непустой —
fail.

---

### 16.3. Code review схем

Перед публикацией:

1. **Model Diff** — что изменилось в модели.
2. **Линтер** («Только новые») — есть ли регрессии.
3. **PII** — если правили сущности с PII, проверить, не появилось
   ли новых.
4. **Publish Preview** — final review diff.
5. Если breaking changes — обсудить с потребителями (другими
   доменами).

---

### 16.4. Работа с PII

1. **Регулярный аудит** (раз в месяц).
2. **Перед рефакторингом** — проверить, не PII ли поле.
3. **При экспорте** — не выгружать PII в тестовые данные.
4. **Baseline** — принять текущее состояние, следить за новыми
   критичными PII.

---

### 16.5. Рефакторинг

Перед **удалением** сущности:

1. **Симуляция удаления** — оценить breaking changes.
2. **План миграции** — следовать шагам.
3. **Обновить потребителей** — сначала сделать замену в ссылающихся
   домах, потом удалить.

Перед **изменением типа** атрибута:

1. **Impact analysis** — кто читает/пишет.
2. **Baseline** — принять, чтобы видеть только регрессии.
3. Создать **новый** атрибут с новым типом (не менять существующий)
   — если есть данные.
4. Мигрировать данные.
5. Удалить старый.

## 18. Troubleshooting

### Q: Приложение не запускается, ошибка EADDRINUSE

Порт 3000 занят. Используйте `--port 3001` или закройте старое
приложение.

### Q: Логин на сервере не проходит

- Проверьте `--login` / `--password`.
- Проверьте доступность `<server>/api/evo/core/bff/graphql`.
- Если инсталляция с самоподписанным сертификатом — используйте
  `--secure=false` (или **без** `--secure` — по умолчанию не
  проверяется).

### Q: В редакторе не работает автокомплит

- Проверьте, что Monaco загрузился (не должно быть `Загрузка Monaco…`
  дольше 5 секунд).
- Если air-gapped — Monaco грузится с CDN, что может не работать.
  (Это известное ограничение.)

### Q: Модель не видит мои правки

- Нажмите **Ctrl+S** — модель пересобирается после сохранения.
- Или перезагрузите страницу.

### Q: Проблемы в линтере не совпадают с реальностью

- Клиентский линтер работает на **сохранённой** версии.
- Если правите YAML — нажмите **Ctrl+S** или **☁** (серверная
  валидация).
- Метка **⏱** рядом с проблемой = «требуется сохранение».

### Q: Publish не проходит с ошибкой LOWER_VERSION

Увеличьте `version` в схеме. Или согласитесь на авто-bump при
публикации (приложение предложит).

### Q: Baseline не сохраняется

- Проверьте права на `<rootDir>/.lint-baselines/` (local) или
  `<cache>/.cache/.lint-baselines/` (remote).
- Если `--reset-cache` — baseline для **нестандартного** cacheDir
  может снестись. Стандартный — переживает.

### Q: Не могу сохранить, «файл заблокирован»

Нажмите **🔒** в шапке или двойной **Shift**.

### Q: Мои правки пропали после перезапуска

- Проверьте `sessionStorage` в DevTools.
- `sessionStorage` ограничен 5 МБ — большие файлы не бэкапятся.
- Бэкап удаляется после успешного сохранения — если не сохраняли,
  бэкап должен быть.

### Q: Diff не показывает изменений

- Diff previous работает, только если `.previous/` существует
  (предыдущее сохранение было).
- Diff published — только в remote с активным draft.

## 19. FAQ

### Чем это отличается от самой R-EVO?

R-EVO — это **runtime** и **UI платформа**. Domains Analyzer —
**инструмент разработки и анализа схем**. Он помогает:

- писать схемы быстрее (генератор, сниппеты, автокомплит);
- находить ошибки (линтер, валидация);
- понимать структуру (граф, каталоги, матрицы);
- аудировать PII (отчёт для DPO);
- безопасно публиковать (diff, preview, baseline).

### Можно ли использовать для legacy-схем?

Да. Все существующие `.ro` файлы подхватываются. Линтер покажет,
где не хватает `description`, где camelCase нарушен и т.д. Baseline
позволит «принять как есть» и следить за регрессиями.

### Работает ли без интернета?

- Local-режим работает **полностью** без сети (кроме Monaco и
  marked с CDN).
- Remote/hybrid — требуют доступа к серверу.
- Для air-gapped инсталляций — нужен форк с локальным Monaco.

### Как экспортировать схему для документации?

- **Экспорт в Markdown** — полная документация домена.
- **Mermaid classDiagram** — ER-диаграмма.
- **Mermaid graph TD** — граф доменов.
- **CSV** — для Excel.

### Как сравнить окружения (DEV / STAGING / PROD)?

Прямого механизма нет. Варианты:

1. Запустить приложение с `--server` на DEV, сохранить snapshot
   (данные → снимок).
2. Переключиться на PROD, загрузить snapshot из DEV, приложение
   покажет diff графа.
3. Для **одного** домена — **DomainCompareModal**: но это работает
   только в рамках одного запуска.

*(См. «Известные ограничения» ниже.)*

### Как поймать регрессии в CI?

1. В pipeline: `npm start -- --server ...` → `--refresh`.
2. Принять baseline вручную перед merge.
3. В следующем запуске — `compareWithBaseline`.
4. Fail, если `totalNew > 0`.

*(Требует доработки: сейчас нет headless-режима. В бэклоге.)*

### Как поддержать «согласование» перед публикацией?

Прямого approval-флоу нет. Используйте:

1. **Publish Preview** с diff.
2. **Model Diff** для review.
3. **Baseline** для контроля регрессий.
4. Публикация — только после согласования с ревьюерами через
   внешние каналы (Jira, Slack).

*(В бэклоге: workflow draft → review → approved → published.)*

### Как найти, где используется атрибут?

**Ctrl+Shift+A** → поиск по имени → клик на сущность → в каталоге
вкладка «Используется». Или в редакторе — курсор на атрибуте → правая
панель «Используется».

### Как найти дубликаты сущностей?

**Ctrl+Shift+M** (матрица связей) — плотные кластеры. Или
**Ctrl+Shift+E** → фильтр «Только сироты» + minimum refs = 0.

### Как увидеть, что изменилось после обновления с сервера?

Тулбар → **Данные → Что изменилось в модели**. Или Sidebar →
«Что нового».

### Где я могу посмотреть все доступные сниппеты?

Откройте YAML-редактор → **⋯ меню → Шпаргалка** → раздел
«Сниппеты». Или **Ctrl+Shift+L** → 📖 рядом с категорией.

### Что такое «манифест» и где он лежит?

`_generated.json` в корне домена. Хранит историю генерации:
`blockId`, `hash`, `title`, `generatedAt`. Используется для
определения «актуален / изменён / удалён».

## Известные ограничения

- **CDN-зависимости**: Monaco и marked грузятся с
  `cdnjs.cloudflare.com` / `jsdelivr.net`. Не работает в air-gapped
  без доработки.
- **Нет версионирования**: только diff между двумя последовательными
  состояниями. Полной истории нет.
- **Нет approval-флоу**: публикация мгновенная.
- **Нет headless-режима**: для CI нужен доработка.
- **Сравнение окружений**: работает только для двух доменов в рамках
  одного запуска.
- **Нет bulk-edit**: массовые правки views / actions / rules —
  вручную.
- **Нет шаблонов сущностей**: `GenerateSchemaModal` не создаёт
  сущность с нуля, только обвязку для существующей.
